# Safety Stock — จุดสั่งซื้อและจุดสั่งซื้อซ้ำ คลังลาดกระบัง — Design

วันที่: 2026-08-18 · สถานะ: อนุมัติแนวทางแล้ว (รอ review spec)

## 1. ปัญหาและเป้าหมาย

ทีม store ลาดกระบังตั้ง **min / max** ไว้ในระบบ ATMS รายรหัสสินค้า แต่ตัวเลขนั้นตั้งไว้เฉยๆ ไม่มีอะไรมาบอกว่า:

- ตั้งไว้ถูกหรือเปล่า — เทียบกับการใช้จริงและเวลารอของแล้วสูงไปหรือต่ำไป
- ตอนนี้รหัสไหน **ต้องสั่งเดี๋ยวนี้** ก่อนของจะขาด
- รหัสไหนตั้ง min/max ไว้ทั้งที่ **ไม่มีใครเบิกเลยทั้งปี**

ผลคือการสั่งของอาศัยความจำและความรู้สึกของคนคุมคลัง ไม่มีตัวเลขรองรับ

**สิ่งที่มีอยู่แล้วและทำไมยังไม่พอ:**

| ของเดิม | ที่อยู่ | ทำอะไร | ทำไมไม่พอ |
|---|---|---|---|
| หน้า SKU index ของ ATMS | mena-atms.com | แสดง min / max / คงเหลือ รายรหัส | เป็นตารางเปล่า ไม่มีการใช้จริง ไม่มี lead time ไม่บอกว่าต้องสั่งอะไร |
| `/deadstock` | mena-wms | FIFO หาของที่รับเข้ามาแล้วไม่ถูกเบิก | มองด้าน "ของเกิน" ไม่ได้มองด้าน "ของจะขาด" |
| `master_data.atms_sku_master` | mena-wms | เก็บ SKU master จาก ATMS | เก็บแค่ `skuPk, code, name, group, warehouse, oracleCode, brand, unit` — **ไม่มี stock/min/max** |

ตรวจด้วย grep ทั้ง `~/Documents/project` และ `~/Documents/cluade_workspace` แล้ว: **ไม่มีที่ไหนเก็บ min/max ลงฐานข้อมูลเลย** มีแต่ CSV snapshot ก้อนเดียวที่ `cluade_workspace/atms-sku-export/atms_sku_inv4.csv` (6 ก.ค. 2026)

**เป้าหมาย:** หน้า `/safety-stock` ใน mena-wms ที่ตอบ 3 คำถามของทีม store:
1. วันนี้ต้องสั่งอะไรบ้าง เท่าไหร่
2. min/max ที่ตั้งไว้ สูงไปหรือต่ำไปเทียบกับการใช้จริง
3. รหัสไหนตั้ง min/max ไว้แต่ไม่มีการเคลื่อนไหว ควรทบทวน

### 2.3 `atms.stockmovement_v5` — การเคลื่อนไหว

โครงสร้างตรวจแล้วในงาน deadstock (ดู `2026-08-14-deadstock-fifo-design.md`) สรุปที่ใช้ในงานนี้:

- แถวรับ: `รับ > 0`, `DD` มีค่า, `ทะเบียน` เป็น `null` เสมอ, **เลข PR ฝังใน `หมายเหตุ`** เช่น `LBPR26050758/71-5742/153/โม่ใหญ่`
- แถวเบิก: `จ่าย > 0`, `WD` มีค่า
- `วันที่` เป็น `Date` จริง · `year_month` เป็น string `"YYYY-MM"`
- ครอบคลุม 2023-01 เป็นต้นมา

**Index บังคับ:** ต้องกรองด้วย `{ inventory_id, year_month }` เท่านั้น — `คลังสินค้า` ไม่มี index จะ collscan 435k แถว

### 2.4 `atms.purchase_requests` — วันที่ขอซื้อ

- คีย์: `"ใบขอสั่งซื้อ (PR)"` · วันที่: `"วันที่"` รูปแบบ `DD/MM/YYYY` (string)
- ใช้คู่กับเลข PR ที่แกะจาก `หมายเหตุ` ของแถวรับใน v5 → ได้ lead time จริง
- **ขนาด collection ยังไม่ทราบ** ต้องวัด `explain` ก่อนรันจริง (เฟส 3)

## 3. กติกาคัดกรอง

```
inventory_id = "4"                     ← ลาดกระบังเท่านั้น
กลุ่มสินค้า ไม่ขึ้นต้นด้วย "ค่าแรง"      ← ค่าแรงไม่ใช่ของสต๊อก

```

## 4. สูตร

ทุกสูตรอยู่ใน `lib/safety-stock-core.ts` เป็นฟังก์ชันล้วน ไม่ import อะไรเลย เพื่อให้ทดสอบตรงๆ ด้วย tsx และ **ใช้ไฟล์เดียวกันทั้งฝั่ง job และฝั่งเบราว์เซอร์**

| ตัวแปร | สูตร | เหตุผลที่เลือกแบบนี้ |
|---|---|---|
| **ADU** | ยอดเบิกในหน้าต่าง ÷ จำนวนวันในหน้าต่าง | หน้าต่าง 3/6/12 เดือน เก็บทั้งสามชุด ค่าเริ่มต้น 6 |
| **SD** | SD ของยอดเบิก**รายเดือน** ÷ √(365/12) | ถ้าใช้รายวัน วันที่ไม่เบิกจะเป็น 0 ทำให้ SD บวมและ ADU ต่ำจนสูตรเพี้ยน — อะไหล่เบิกเป็นครั้งคราว ไม่ใช่ทุกวัน |
| **LT** | median(วันที่รับ − วันที่ PR) | median ทนค่าผิดปกติกว่า mean · ทิ้งค่าที่ < 0 หรือ > 365 |
| **SS** | `z × SD × √LT` | z = 1.65 (service level 95%) ปรับได้บนหน้าเว็บ |
| **ROP** | `ADU × LT + SS` | จุดที่ต้องสั่ง |
| **DoS** | `onHand ÷ ADU` | ADU = 0 → "ไม่มีการใช้" ไม่ใช่ ∞ |
| **แนะนำสั่ง** | `max(0, maxQty − onHand)` | ถ้าไม่มี maxQty → `ROP + ADU×LT − onHand` |

### Lead time ลดหลั่น 3 ชั้น

1. **รายรหัส** — ต้องมี ≥ 3 ตัวอย่างใน 24 เดือน
2. ไม่พอ → **ค่ากลางของกลุ่มสินค้า**
3. ไม่พอ → **ค่ากลางทั้งคลัง**

เก็บ `leadTimeSource` (`"sku" | "group" | "warehouse"`) และ `leadTimeSamples` ไว้ในแถว **และแสดงบนหน้าเว็บ** ทีมต้องเห็นว่าเลขไหนเชื่อได้แค่ไหน

### สถานะ — ตัดสินตามลำดับ ไม่ทับกัน

| # | key | เงื่อนไข | ความหมาย |
|---|---|---|---|
| 1 | `no_usage` | ยอดเบิก 12 เดือน = 0 | ตั้ง min/max ไว้แต่ไม่มีใครเบิก — ควรทบทวน เชื่อมกับ `/deadstock` |
| 2 | `out` | `onHand ≤ 0` | ของหมดแล้ว |
| 3 | `below_rop` | `onHand < ROP` | **ต้องสั่งวันนี้** |
| 4 | `below_min` | `onHand < minQty` | ต่ำกว่า min ที่ตั้งไว้ |
| 5 | `over_max` | `onHand > maxQty` | เกิน max จมเงิน |
| 6 | `ok` | นอกนั้น | ปกติ |

**`no_usage` ต้องอยู่อันดับแรก** — ADU, SD, SS, ROP ทั้งหมดคำนวณจากยอดเบิก ถ้าไม่มีการเบิกเลย ตัวเลขที่ตามมาเป็นศูนย์หมดและไม่มีความหมาย การปล่อยให้ตกไปติด `below_min` (เพราะ `onHand = 0 < minQty`) จะทำให้รายการที่ควร**เลิกตั้ง min/max** ไปปนอยู่ในรายการที่**ควรสั่งเพิ่ม** ซึ่งตรงข้ามกันคนละทาง

### ตรวจ min ที่ตั้งไว้ — คุณค่าหลักของหน้านี้

| `minVerdict` | เงื่อนไข | ความหมาย |
|---|---|---|
| `too_low` | `minQty < ROP` | ของจะขาดก่อนของใหม่มาถึง |
| `too_high` | `minQty > ROP × 2` | ตั้งสูงเกินจำเป็น จมเงิน |
| `ok` | นอกนั้น | |

ถ้า `leadTimeSource = "warehouse"` (ไม่มีข้อมูลรายรหัสเลย) ให้ `minVerdict = "unknown"` — **ห้ามตัดสิน min จากค่ากลางทั้งคลัง**

### ทำไม precompute แทนคำนวณตอน request

1. **ATMS ล่มเมื่อยิงรัว** — วัดจริง 2026-08-17: 176 requests ที่ pace 1s ทำให้ error rate ไต่ 0% → 18% → 25% → 40% ใน 35 นาที การดึงจึงต้องเป็น job ที่คุมจังหวะได้ ไม่ใช่ request
2. **ต้นทางอัปเดตวันละครั้งอยู่แล้ว** — v5 เข้าเวลา ~09:15 ICT คำนวณสดไม่ได้ข้อมูลใหม่ขึ้นเลย
3. **การ join หา lead time แพง** — แพงเกินกว่าจะทำทุก request

### เก็บวัตถุดิบ ไม่ใช่แค่ผลลัพธ์

ถ้าตรึง z และหน้าต่างไว้ในฐาน ทีมจะเล่นกับ service level ไม่ได้ ต้องรอ job รอบหน้า

แถวจึงเก็บ **ADU/SD ทั้งสามหน้าต่าง + LT + onHand + min/max** แล้ว:
- job คำนวณด้วยค่าเริ่มต้น (6 เดือน, z=1.65) เก็บ `status`/`rop` ลงฐาน → Mongo เรียง/กรองได้
- หน้าเว็บเลื่อน z หรือสลับหน้าต่าง → เรียก `lib/safety-stock-core.ts` คำนวณใหม่ในเครื่องทันที ไม่ยิง DB
- สูตรมีที่เดียว ไม่มีทางเพี้ยนคนละทาง

~4,000 แถวส่งทั้งก้อน (gzip ประมาณ 300KB) ไม่ต้องแบ่งหน้า

## 6. หน้าเว็บ

### 6.1 `/safety-stock` — หน้าเดียวจบ

**การ์ดบนสุด 4 ใบ**

| การ์ด | ตัวเลข |
|---|---|
| 🔴 ต้องสั่งวันนี้ | จำนวนรหัส + มูลค่าที่ต้องสั่งรวม |
| ⚫ ของหมดแล้ว | จำนวนรหัสที่ `onHand ≤ 0` แต่ยังมีการใช้ |
| 🔵 เกิน max | จำนวนรหัส + มูลค่าที่จมเกินจำเป็น |
| 🟣 min/max ควรทบทวน | `too_low` + `too_high` + `no_usage` |

**ตาราง** คอลัมน์ตรึงซ้าย (รหัส/ชื่อ) เลื่อนแนวนอนได้ ตามแบบ `/deadstock/pending`

```
รหัส · ชื่อ · กลุ่ม · หน่วย ‖ คงเหลือ · min · max ‖ เฉลี่ย/วัน · จำนวนครั้งที่เบิก ·
LT(ที่มา) · ROP · SS · พอใช้อีกกี่วัน ‖ สถานะ · ตรวจ min · แนะนำสั่ง
```

> **"จำนวนครั้งที่เบิก" ห้ามตัดออก** — อะไหล่เบิกเป็นครั้งคราว ADU จึงออกมาเป็น 0.03/วัน ซึ่งถูกตามทฤษฎีแต่ดูไม่น่าเชื่อ ถ้าไม่แสดงว่า "12 เดือนเบิก 4 ครั้ง" ควบคู่กัน ทีมจะไม่เชื่อทั้งตาราง

**ตัวกรอง** ค้นหารหัส/ชื่อ · กลุ่มสินค้า (`MultiSelectCombobox` ที่มีอยู่) · ชิปสถานะ · หน้าต่าง 3/6/12 เดือน · service level 90/95/99%

**คลิกแถว → dialog** กราฟยอดเบิก 12 เดือน · ล็อต FIFO ที่ค้างพร้อมอายุ · ประวัติ PR→รับของที่ใช้คำนวณ LT

**Export Excel** ตามที่กรองอยู่ (ใช้ `xlsx` ที่มีในโปรเจกต์)

## 10. สิ่งที่ไม่ทำในรอบนี้ (YAGNI)

- คลังอื่นนอกจากลาดกระบัง (แต่โค้ดรับ `inventoryId` เป็นพารามิเตอร์ ไม่ hardcode)
- เขียน min/max กลับเข้า ATMS
- แจ้งเตือนอัตโนมัติ (อีเมล/LINE)
- สร้าง PR อัตโนมัติจากรายการที่ต้องสั่ง
- เก็บ snapshot ย้อนหลังดูแนวโน้ม
- EOQ / ต้นทุนการสั่งซื้อ
