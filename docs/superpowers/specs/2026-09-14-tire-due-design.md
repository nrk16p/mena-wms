# แท็บ "ยางถึงกำหนดเปลี่ยน" — Design

วันที่: 2026-09-14 · หน้า `/tire` (`components/tire/fleet-page.tsx`)

## ปัญหา

วันนี้หน้า `/tire` บอกได้แค่ "ยางเส้นนี้ใส่มานานแค่ไหน" (อายุตาม `changeIn`) และ "% คงเหลือ"
ซึ่งคำนวณได้เฉพาะตอนเปิดรถทีละคัน และต้องมีเลขไมล์จากคำขอ/ประวัติ — วางแผนล่วงหน้าไม่ได้
ต้องการมุมกลับ: **ทั้งฟลีต เส้นไหนใกล้หมดอายุการใช้งานตามระยะทางจริง** เพื่อสั่งซื้อ/นัดเปลี่ยนก่อนยางหมด

## นิยาม

```
กม.ใช้ไป = ระยะทางสะสมของทะเบียนนั้น ตั้งแต่ changeIn → วันนี้
%ใช้ไป   = กม.ใช้ไป ÷ ระยะทางที่กำหนดของรุ่นยาง × 100

≥ 100%  over    🔴 เกินกำหนด
≥  90%  due     🟠 ถึงกำหนดเปลี่ยน   ← เกณฑ์แจ้งเตือนหลัก
≥  80%  warn    🟡 เฝ้าระวัง
<  80%  ok
```

เกณฑ์ 90/80 อยู่ที่ `lib/tire-due.ts` ที่เดียว ทั้ง API และ UI อ่านตัวเดียวกัน

## แหล่งข้อมูลระยะทาง (ลำดับความสำคัญ)

| ลำดับ | แหล่ง | ที่มา | ครอบคลุม (สำรวจ 2026-09-14) |
|---|---|---|---|
| 1 | GPS | api-ncac `POST /drivingdistance/sumdistance` → `datalake.drivingdistance` | 601/1,109 ทะเบียน · ล่าสุด D-2 |
| 2 | ค่าเที่ยว | `atms.truck_distance_summary` (logic เดียวกับ `/truck-distance` ของ mena-intelligence) | 851/1,109 ทะเบียน · อัปเดตทุกคืน 02:35 · มีทั้ง `type: head` และ `tail` |

- รวม 2 แหล่ง = 852/1,109 ทะเบียน → ยางที่คำนวณได้ 8,186/10,329 เส้น
- ตรวจสอบแล้วเดือน ส.ค. 2026 คันที่มีทั้งสองแหล่ง GPS/ค่าเที่ยว = 97–106% → สลับแหล่งกันแล้วตัวเลขไม่กระโดด
- **ยางหาง (ตำแหน่ง RB…)** ใช้ `truck_distance_summary` `type: "tail"` เท่านั้น — GPS เก็บเฉพาะทะเบียนหัว

### ฟอร์แมตทะเบียน

## วิธีคำนวณ — รายเดือน ไม่ใช่รายวัน

ยางแต่ละเส้นเริ่มนับคนละวัน (2,732 คู่ ทะเบียน×วันเปลี่ยนเข้า / 991 วันไม่ซ้ำ)
ถ้ายิง GPS ทีละคู่ = พันกว่า request ต่อรอบ ช้าเกินรับได้

**แทนด้วยการดึงยอดรายเดือนทั้งกองเดือนละครั้ง** (`sumdistance` ไม่ส่ง `plate_number` = ได้ทุกทะเบียน)
→ ~24 request ต่อรอบ แล้วประกอบเอง:

```
kmUsed(tire) = km(เดือนของ changeIn) × (วันที่เหลือในเดือนนั้น ÷ วันทั้งเดือน)
             + Σ km(เดือนถัดมาจนถึงเดือนก่อนปัจจุบัน)
             + km(เดือนปัจจุบัน) × (วันที่ผ่านมา ÷ วันทั้งเดือน)
```

ฝั่งค่าเที่ยวเป็นรายเดือนอยู่แล้ว — query เดียวได้ครบทุกเดือนทุกทะเบียน

**ความคลาดเคลื่อนที่ยอมรับ:** การเฉลี่ยภายในเดือนแรกคลาด ±หลักร้อย กม. — เทียบกับเกณฑ์ 90% ของระยะหลักแสน ถือว่าไม่มีนัยสำคัญ และหน้าเว็บจะระบุว่าเป็น "ประมาณการ"

## ระยะทางที่กำหนด (ต่อรุ่นยาง)

สภาพปัจจุบัน: `tire_stock.distance` = 0 ทุกเส้น · `tire_spec_master` มี 9 รายการ แต่ชื่อจาก ATMS เป็นชื่อกลางๆ ไม่มียี่ห้อ → แมตช์ได้ 2/67 รุ่น

**ทางออก:** ใช้ `/tire/master` (`tire_spec_master`) เป็นแหล่งเดียวต่อไป แต่
1. เพิ่มการจับคู่ด้วย **`productName` ตรงกับชื่อสินค้าจาก ATMS** (normalize ช่องว่าง/ตัวพิมพ์) — ของเดิมที่จับด้วย brand+size+model ยังทำงานเหมือนเดิม
2. Seed 67 รุ่นที่ใช้อยู่จริงเข้า `tire_spec_master` พร้อมค่าเริ่มต้นตามชนิดยาง ติดธง `needsReview: true`
3. หน้า `/tire/master` แสดง **จำนวนเส้นที่ใช้อยู่** ต่อรุ่น + ป้าย "รอยืนยันระยะ" → รู้ทันทีว่าต้องแก้ตัวไหนก่อน

ลำดับการหาระยะของยาง 1 เส้น: `tire_stock.distance` (>0) → `tire_spec_master` ตาม `productName` → ตาม brand+size+model → ไม่พบ = กลุ่ม "ยังไม่ตั้งระยะกำหนด"

## สถาปัตยกรรม

```
cron /api/cron/tire-sync (02:00 เดิม)
  └─ sync ATMS → tire_change        (เดิม)
  └─ rebuildTireDistance()          (ใหม่)
        ├─ อ่าน tire_change {isLatest, changeIn != null}
        ├─ GPS: sumdistance รายเดือน × ~24 เดือน   ┐
        ├─ ค่าเที่ยว: truck_distance_summary 1 query ┘ → แผนที่ {plate → {month → km}}
        ├─ ระยะกำหนด: tire_stock / tire_spec_master
        └─ upsert → tire_distance (1 doc = ยาง 1 เส้น)

GET  /api/tire-due     → อ่าน tire_distance (เร็ว) + summary นับตามระดับ
POST /api/tire-due     → สั่งคำนวณใหม่เอง (ปุ่มบนหน้า)
PATCH /api/tire-due/[id] → snooze / ยกเลิก snooze
```

**ทำไมต้อง snapshot:** ยิง GPS สดตอนเปิดหน้า = api-ncac บน Render มี cold start และต้องรอหลาย request · snapshot ทำให้แท็บเปิดปุ๊บติดปั๊บ และกดคำนวณใหม่เองได้เมื่อต้องการ

### `tire_distance` (collection ใหม่)

```js
{
  branch, plate, unit: "head"|"trailer",
  serialNo, tirePosition, positionCode, product,
  changeIn: Date,
  kmUsed: Number,          // ประมาณการจากแหล่งข้อมูล
  source: "gps"|"trip"|"none",
  specDistance: Number,    // 0 = ยังไม่ตั้งระยะกำหนด
  specSource: "stock"|"spec-name"|"spec-model"|"none",
  usedPct: Number|null,
  level: "over"|"due"|"warn"|"ok"|"unknown",
  ageDays: Number,
  snoozedUntil: Date|null,
  computedAt: Date,
  dataThrough: Date        // ข้อมูลระยะทางถึงวันไหน (GPS ช้า 2 วัน)
}
```
index: `{ branch:1, level:1 }`, `{ plate:1, serialNo:1 }` (unique)

## UI — แท็บที่ 4

ต่อจาก `รถทุกคัน / คำขอ-อนุมัติ / ประวัติการเปลี่ยน` → เพิ่ม **`ยางถึงกำหนดเปลี่ยน`** (icon `AlertTriangle`)
badge = จำนวนเส้น `level ∈ {over, due}` ที่ยังไม่ snooze (เฉพาะสาขาที่ผู้ใช้เห็นได้ ใช้ `useBranchScope` เดิม)

- **การ์ดสรุป 3 ใบ** คลิกกรองได้: เกินกำหนด / ถึงกำหนด / เฝ้าระวัง
- **ตาราง** 1 แถว = ยาง 1 เส้น เรียง `%ใช้ไป` มาก→น้อย:
  ทะเบียน · ตำแหน่ง · รุ่นยาง · Serial · เปลี่ยนเข้า · อายุ · กม.ใช้ไป · ระยะกำหนด · แถบ % + ป้ายสี · แหล่ง (GPS/ค่าเที่ยว) · ปุ่ม
- **ตัวกรอง** หัว/หาง + ค้นหาทะเบียน (สาขาใช้ตัวกรองร่วมของหน้าเดิม)
- **ปุ่มต่อแถว**: `เปิดหน้ารถ` (ไปหน้า VehicleDetail คันนั้นเพื่อสร้างคำขอเปลี่ยน) · `ไม่ต้องแจ้ง` (snooze 30 วัน — ตัดจาก badge แถวจางลง ยกเลิกได้)
- **ท้ายตาราง** กลุ่มพับเก็บ: `ยังไม่ตั้งระยะกำหนด (N เส้น)` พร้อมลิงก์ `/tire/master` · `คำนวณระยะไม่ได้ (N เส้น)` = ไม่มีวันเปลี่ยนเข้า หรือทะเบียนไม่มีทั้ง GPS/ค่าเที่ยว
- **แถบบอกสถานะข้อมูล**: `ข้อมูลระยะถึง <dataThrough> · คำนวณล่าสุด <computedAt>` + ปุ่ม `คำนวณใหม่`

## ขอบเขตที่ไม่ทำ (YAGNI)

- ไม่ส่ง LINE/อีเมล — แจ้งเตือนผ่าน badge บนหน้าเว็บก่อน ถ้าต้องการค่อยต่อยอด
- ไม่สร้างคำขอเปลี่ยนยางอัตโนมัติ — คนกดเองผ่านหน้ารถเหมือนเดิม
- ไม่แก้สูตร `remainingPct` เดิมในหน้ารถ (คนละฐาน: อันนั้นใช้เลขไมล์ อันนี้ใช้ระยะทางสะสม) — แสดงคู่กันได้ ไม่ทับกัน

## ความเสี่ยง / ข้อจำกัดที่ยอมรับ

| เรื่อง | ผลกระทบ | การรับมือ |
|---|---|---|
| GPS ช้า 2 วัน (Jenkins รัน UTC) | %ใช้ไป ต่ำกว่าจริงเล็กน้อย | แสดง `ข้อมูลระยะถึง <วันที่>` บนหน้า |
| 979 เส้นไม่มี `changeIn` | คำนวณไม่ได้ | แยกกลุ่ม "คำนวณระยะไม่ได้" |
| 257 ทะเบียนไม่มีทั้ง GPS/ค่าเที่ยว | คำนวณไม่ได้ | กลุ่มเดียวกัน + แสดงอายุยางแทน |
| `changeIn` บางเส้นเป็นวันอนาคต (พบ 2026-09-28) | %ใช้ไป ติดลบ | clamp `kmUsed >= 0` + ไม่ขึ้นเตือน |
| `tire_change` มีแค่ index `_id` (69k docs) | rebuild สแกนทั้ง collection | เพิ่ม index `{ isLatest: 1 }` (ขอยืนยันก่อนสร้าง) |
| ค่าเริ่มต้นระยะกำหนดเป็นค่าประมาณ | เตือนเร็ว/ช้ากว่าจริง | ติดธง `needsReview` ให้ฝ่ายซ่อมบำรุงยืนยันทีละรุ่น |

## สิ่งที่เปลี่ยนจากดีไซน์ระหว่างทำจริง

| เรื่อง | เหตุผล |
|---|---|
| ตัด **ยางอะไหล่** (RB13 / ชื่อตำแหน่งมี "อะไหล่") ออกจากกลุ่มเตือน | รอบทดสอบแรกยางอะไหล่ขึ้น "เกินกำหนด" 38 เส้น ทั้งที่ยังไม่ได้แตะถนน — ย้ายไปกลุ่ม `ยางอะไหล่` แยกต่างหาก |
| ตัด `ยางรองคอใหม่` / `ถอดแกะยาง` ออกจาก snapshot | ATMS บันทึกงานที่ไม่ใช่ "ยาง 1 เส้น" ปนมาในช่องชื่อสินค้าเดียวกัน |
| เพิ่ม route `/api/cron/tire-distance` (ป้องกันด้วย `CRON_SECRET`) | ไว้รันคำนวณซ้ำโดยไม่ต้อง sync ATMS ใหม่ — ใช้ตอนรอบกลางคืนดึง GPS ไม่ครบ หรือหลังแก้ระยะกำหนด |
| สร้าง index ให้ `tire_distance` ตอนเริ่มรอบ | upsert หมื่นครั้งต่อรอบ ไม่มี index = 69 วินาที มี index = 23 วินาที |
| `/tire/master` โชว์ **จำนวนเส้นที่ใช้อยู่** + ป้าย "รอยืนยัน" และเรียงตามจำนวนเส้น | ระยะกำหนดที่ตั้งผิดกลายเป็นการเตือนผิด คนตั้งค่าต้องเห็นก่อนว่าแถวนั้นกระทบยางกี่เส้น |
| ไม่เพิ่ม cron entry ใหม่ — เรียก `rebuildTireDistance()` ต่อท้าย `tire-sync` | รอบเต็มใช้ 23 วินาที รวมกับ sync แล้วยังห่างจากลิมิต 300 วินาทีมาก |
